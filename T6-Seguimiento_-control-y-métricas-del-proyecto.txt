Earned Value Management (EVM)

Si queremos medir alcance, tiempo y coste simultáneamente, necesitamos algo más que “% completado”.

EVM formaliza con números el triángulo:
                                                A




                                          T              C




           EVM convierte el equilibrio del proyecto en magnitudes medibles.
Deﬁniciones formales en EVM

En EVM trabajamos con tres magnitudes básicas.

 ●   Planned Value (PV): Valor presupuestado del trabajo que debería haberse completado hasta una
     fecha determinada.

      ○   Si el proyecto cuesta 10k€ y en la semana 4 debería estar al 40%: PV = 10k × 0.40 = 4k €

 ●   Earned Value (EV): Valor presupuestado del trabajo que realmente se ha completado.

      ○   Si realmente se ha completado el 30% del proyecto: EV = 10k × 0.30 = 3k €

 ●   Actual Cost (AC): Coste real incurrido hasta la fecha.

      ○   Si el equipo ha gastado 4k5 € en salarios hasta la semana 4: AC = 4k5 €
Fórmulas fundamentales en EVM

●   Schedule Variance (SV): Indica desviación en tiempo (en términos monetarios).

     ○   SV = EV − PV

           ■   Si: EV = 3k, PV = 4k
           ■   SV = 3k − 4k = −1k
           ■   Negativo → retraso.
●   Cost Variance (CV): indica desviación en costes.

     ○   CV = EV − AC

           ■   Si: EV = 3k, AC = 4k5
           ■   CV = 3k − 4k5 = −1k5

           ■   Negativo → sobrecoste.
Índices de rendimiento en EVM

●   Schedule Performance Index (SPI)

     ○   SPI = EV / PV

          ■   SPI = 1 → en plazo.
          ■   SPI < 1 → retraso.
          ■   SPI > 1 → adelantado.
●   Cost Performance Index (CPI)

     ○   CPI = EV / AC

          ■   CPI = 1 → en presupuesto.

          ■   CPI < 1 → sobrecoste.

          ■   CPI > 1 → ahorro.
¿Es necesario usar siempre EVM formalmente?

No es necesario utilizar EVM formalmente siempre.

Pero debéis entender:

 ●   El proyecto puede ir retrasado y con sobrecoste simultáneamente.

 ●   Puede ir en plazo pero con sobrecoste.

 ●   Puede ir con ahorro pero con retraso.




        El sistema puede estar desequilibrado en varias dimensiones a la vez.

Cobertura de código

      Cobertura = (Líneas ejecutadas por test / Líneas ejecutable totales ) * 100

 ●   Mide cuánto código ha sido ejecutado al menos una vez por tests.

 ●   Es un indicador de esfuerzo en validación automatizada.

Tasa de defectos

                Tasa de defectos = Número de defectos / Tamaño software

El tamaño puede medirse como KLOC (mil líneas de código), número de módulos, número de historias
implementadas.

Si un módulo tiene:

 ●   3 defectos por cada 1000 líneas
 ●   otro tiene 15 defectos por cada 1000 líneas

¿Dónde está el problema estructural?

Cada defecto implica tiempo de análisis, tiempo de corrección, nuevas pruebas, posible regresión.
Deuda técnica

        Sobrecoste por tarea = Tiempo real actual − Tiempo histórico estimado

La deuda técnica se observa cuando:

 ●   Cada nueva funcionalidad cuesta más que la anterior.

 ●   Aparecen efectos colaterales inesperados.

 ●   El equipo evita tocar ciertas partes del código.

 ●   Se retrasan refactorizaciones “para después”.

Si sistemáticamente crece → hay deuda.

CI / CD
 ●   CI → Continuous Integration (Integración Continua)

       ○   Cada cambio se valida automáticamente.

 ●   CD → Continuous Delivery o Continuous Deployment

       ○   Cada versión es generable automáticamente.

Son prácticas de ingeniería que automatizan la validación del software cada vez que se modiﬁca el
código.

Es el mecanismo técnico que automatiza integración, validación, pruebas, generación de métricas.



                        La ingeniería moderna automatiza el control
Continuous Integration (CI)
 ●   Cada vez que alguien sube código al repositorio,

 ●   El sistema automáticamente:

       ○   compila el proyecto,
       ○   ejecuta los tests,
       ○   analiza calidad,
       ○   genera cobertura,
       ○   veriﬁca que todo sigue funcionando.

No se espera al ﬁnal del sprint. No se espera a “cuando haya tiempo”. Se valida continuamente.




       CI convierte cada cambio en un experimento validado automáticamente.
Continuous Delivery / Deployment (CD)
 ●   Continuous Delivery

       ○   El sistema genera automáticamente una versión lista para desplegar, pero la publicación
           puede ser manual.

 ●   Continuous Deployment

       ○   Cada cambio validado se despliega automáticamente en producción.

Lo importante es entender:

 ●   Que el producto puede generarse automáticamente.

 ●   Que el estado es siempre veriﬁcable.

 ●   Que la integración es continua.
¿Cómo funciona técnicamente CI/CD?
1.   Un estudiante hace un commit en GitHub.

2.   Se activa un pipeline.

3.   El sistema:

      ○    compila,

      ○    ejecuta tests,

      ○    calcula cobertura,

      ○    ejecuta análisis estático,

      ○    genera informe.

4.   Si algo falla → el equipo lo sabe inmediatamente.

Conclusión
Riesgo → posibilidad futura.

Seguimiento → detección temprana de que el riesgo se está materializando.

El seguimiento convierte riesgos en información gestionable.

En vuestro proyecto deberíais poder responder a:

 ●   ¿Qué estáis controlando?
 ●   ¿Qué indicadores miráis?
 ●   ¿Qué haríais si detectáis desviación?
 ●   ¿Habéis revisado el plan?
